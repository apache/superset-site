MCP Server Deployment & Authentication

Superset includes a built-in Model Context Protocol (MCP) server that lets AI assistants -- Claude, ChatGPT, and other MCP-compatible clients -- interact with your Superset instance. Through MCP, clients can list dashboards, query datasets, execute SQL, create charts, and more.

This guide covers how to run, secure, and deploy the MCP server.

Looking for user docs?

See Using AI with Superset for a guide on what AI can do with Superset and how to connect your AI client.

Tool deadlines and concurrency​

Protected synchronous and asynchronous MCP tools run in isolated thread workers, each with its own Flask app context and metadata database session. Warehouse I/O does not run on the transport event loop. This includes SQL execution, chart data and previews, chart compilation, dataset queries, and tools that discover warehouse metadata.

MCP_TOOL_WORKERS sets the maximum admitted warehouse-capable calls per application/process. A full pool immediately returns an MCP server busy error; it does not queue requests behind slow queries.

Tools that only read Superset's metadata database (the list_* and get_*_info tools, get_schema, get_instance_info, health_check, and similar) are admitted under a separate bound, MCP_METADATA_TOOL_WORKERS, so they keep answering while slow warehouse queries fill MCP_TOOL_WORKERS. A metadata-only tool that does reach a warehouse must first take a MCP_TOOL_WORKERS slot, and reports MCP server busy if none is free. Setting MCP_METADATA_TOOL_WORKERS = 0 admits every tool under MCP_TOOL_WORKERS.

Both bounds come out of one budget: the metadata pool's capacity, pool_size + max_overflow. A warehouse-capable call can hold a metadata connection for the whole of its warehouse query and cancelling it needs another; a metadata-only call holds at most one; and the server's own metadata I/O (tool-list filtering, audit writes, error hooks) runs on one bounded thread, and API-key lookups on another of their own, so requests with unknown keys cannot delay audit writes or RBAC filtering. Admission keeps 2 * MCP_TOOL_WORKERS + MCP_METADATA_TOOL_WORKERS + 2 within the capacity, so even with every slot in use no metadata connection checkout waits for another holder. By default (None) warehouse-capable calls get about a third of the connections left after those two threads, and metadata-only calls what remains, each up to 16. With SQLAlchemy's default pool (5 + 10 connections) that is 4 warehouse-capable and 5 metadata-only calls. To admit more, raise the pool for the MCP process, for example SQLALCHEMY_ENGINE_OPTIONS = {"pool_size": 20, "max_overflow": 20} (12 and 14). Explicit values above the budget are reduced with a startup warning, and a pool with fewer than 4 connections is rejected at startup. The server never waits for a metadata connection on its event loop.

Pool logs report initialization and connection-budget clamping without logging configuration values or engine-derived counts. Successful transport-layer API-key validation logs the user id rather than the username or API key.

Tool-list and search permission checks, success/error audit writes, response-size audits, and error hooks run in metadata threads with independent Flask contexts and scoped sessions. These sessions are cleaned up when the operation finishes, including after failure or client disconnection; inherited request contexts do not share their ORM user/session with the thread.

execute_sql uses its request's timeout (default: 30 seconds). Tools without a timeout parameter use SQLLAB_TIMEOUT. The deadline covers the complete tool call, including composed queries, and returns a clear timeout error with a call ID. Superset requests warehouse cancellation using its engine cancellation hooks, including for connection prequeries, on a separate bounded pool. Cancellation connections run independently of the expired tool deadline, including connection prequeries such as PostgreSQL schema selection. Trino's client only learns a query's queryId once it is running and then blocks until results arrive, so the cancellation thread reads that id from the live cursor and kills the query with system.runtime.kill_query. Engines whose specs expose no cancellation handle (for example BigQuery, Databricks native and Athena) are not cancelled. Drivers without cancellation support can continue running after the caller receives the timeout; the worker retains its slot and owns session cleanup until it finishes, while metadata-only tools keep their own bound. A stuck cancellation also retains its call's slot rather than exhausting cancellation capacity for new calls. One warning with the call ID records abandonment. A timeout does not guarantee that warehouse writes were rolled back, so do not blindly retry mutating SQL.

Externally managed dashboards​

MCP dashboard mutation tools refuse changes to externally managed dashboards, including ownership and access-role changes, layout and filter edits, chart membership, certification, deletion, and restoration. Their responses set managed_externally: true and explain that the external system is the source of truth; changing Superset permissions or retrying does not override it. Read-only dashboard tools and certification's inspect-only call remain available.

Native filter defaults​

manage_native_filters accepts default_value for select filters. An empty list clears the selection. With enable_empty_filter: true, that explicit empty default matches no rows in both the dashboard UI and server-side dashboard chart queries, including for UI-created non-exact select filters. Creating a required select filter without default_value also stores this match-nothing default, unless default_to_first_item is enabled. Inverse-selection filters retain the UI's no-predicate behavior for empty selections. Disabling enable_empty_filter removes the empty default's match-nothing predicate without requiring another default_value update. Explicit defaults, including an empty list, cannot be combined with default_to_first_item: true. Creating a first-item filter or enabling that option on an existing filter leaves the stored selection unset so the dashboard can choose the first available item after loading options. Toggling enable_empty_filter on a first-item filter preserves that behavior rather than storing an explicit empty selection or match-nothing predicate. Any update to a first-item filter also clears a defined legacy stored selection (including null) when first-item mode remains enabled, allowing automatic selection. Select filters with legacy string-column targets support both default updates and applied selections.

Bounding dashboard dataset metadata​

get_dashboard_datasets lists a dashboard's datasets and semantic views with column and metric details. Its optional max_columns and max_metrics parameters limit the number of columns (0–100, default 100) and metrics (0–50, default 50) returned per dataset. Columns and metrics are sorted by name before the caps apply, so repeated calls return the same subset. For a wide dashboard, start with smaller caps or omit the details entirely:

{
  "request": {
    "identifier": 123,
    "max_columns": 0,
    "max_metrics": 0
  }
}

Dataset identities, chart counts, and total column and metric counts are retained. columns_truncated and metrics_truncated are true whenever fewer items are returned than the dataset contains, including when a cap of 0 omits a nonempty list. Use get_dataset_info to fetch details for an individual dataset. Omitting both parameters returns up to 100 columns and 50 metrics per dataset. The caps bound per-dataset details, not the number of datasets or the entire response's byte size; a dashboard with many datasets can still exceed the server's configured byte limit.

Dashboard filter notifications​

apply_dashboard_filters supports exact-match select filters without inverse selection, time filters, numeric range filters, and time-grain filters. Range bounds must be finite numbers representable as floats, or null; booleans are rejected. Range permalink labels use the dashboard's smart number formatting with ASCII minus signs, falling back to plain numeric representations if formatting overflows; time-grain labels come from the target datasource's grain names when available. Time grains must be supported by the filter's target dataset's database engine, as listed in the datasource's time_grain_sqla options. If the filter has a nonempty configured allowlist, the selected grain must also appear in that list. An unresolved target dataset is rejected. Inverse-selection configurations are rejected. Select filters configured for contains, starts-with, or ends-with matching are rejected rather than silently applying exact matching. A single-select filter accepts at most one value; a longer list is rejected rather than stored as a selection the control cannot render. Clearing a required select filter with values: [] matches no rows, including when opening the returned permalink; an explicit clear does not restore its saved default.

Returned dashboard permalink URLs use WEBDRIVER_BASEURL_USER_FRIENDLY as the public origin and respect APPLICATION_ROOT (or the request's WSGI SCRIPT_NAME when mounted behind a proxy). Set the public URL to the browser-accessible Superset host; the MCP service's own host may be different.

To stack filters across chat turns, pass the previous apply_dashboard_filters response's permalink_key as base_permalink_key in the next request for the same dashboard. For example, apply Region = EMEA, then pass that key with a Time Range = 2024-01-01 : 2025-01-01 request to keep EMEA and add the year constraint. Each new value replaces that filter's entire prior entry; unmentioned filters persist. Omit the base key to start from dashboard defaults. applied_filters summarizes only the new request, not the inherited selections. Inherited entries for filters the dashboard no longer defines are dropped, so a filter deleted or recreated between turns does not carry a stale predicate forward.

Base state is resolved server-side under the calling user's dashboard access and merged without display redaction; the raw base mask is not returned. Missing or expired keys, resolution failures, access denial, and dashboard mismatches fail explicitly without creating a replacement link. Missing and expired keys share an error because the permalink store does not distinguish them.

After creating a dashboard permalink, apply_dashboard_filters attempts a best-effort dashboard.filters_applied realtime notification scoped to the calling principal. Its payload contains only dashboard_id and permalink_key; filter values and resolved state are not included. Consumers must resolve the key through the dashboard's authorized permalink load path.

Live browser updates require WEBSOCKET_ENABLE = True, a configured DISTRIBUTED_COORDINATION_CONFIG backend, a running superset-websocket server, and a strong, non-default WEBSOCKET_JWT_SECRET of at least 32 bytes. WEBSOCKET_URL must also point at a ws:///wss:// endpoint the browser can reach. Its default, ws://127.0.0.1:8080/, resolves to the browser's own loopback, so a remote deployment that leaves it unchanged has every server-side piece configured correctly while live updates never connect. The browser user also needs can_read on Realtime. With the default configuration the realtime half is inert, but the tool still creates and returns a permalink URL. The MCP process and websocket transport must use the same REALTIME_CHANNEL_PREFIX. This publisher does not require the Global Task Framework feature flag.

The response's live_update_pushed field reports publication success, not browser receipt or application. When WEBSOCKET_ENABLE is disabled or unset, no notification is published and this field is false. Without a backend, can_read on Realtime for the calling principal, an identifiable principal, or a successful publish, it is also false; the created dashboard_url remains the fallback. An open dashboard resolves matching notifications through the existing dashboard permalink API and applies the returned filters without a reload. A “Filters applied from chat” toast offers Undo, restoring the affected filters' previous selections. The toast carries an action, so it has no auto-dismiss timer and stays up until Undo or its close button is used, which keeps the action reachable for keyboard and assistive-technology users. Undo restores only the filters whose current state still matches what the notification applied, so a selection edited in the meantime is kept. Filters not present in the notification's permalink keep their existing selections in the open dashboard.

Reconnect deliberately does not fetch or replay filter state: there is no latest-per-user permalink lookup, and replaying a previously received permalink could overwrite manual changes or undo. If a notification is missed or its permalink cannot be resolved, open dashboard_url from chat.

Dashboard filter scope​

A client that answers questions about a dashboard the user is viewing (for example an assistant embedded next to it) can make every tool call honor that dashboard's active filters by sending them in the X-Superset-Dashboard-Scope request header on each MCP HTTP request of the conversation turn. The model issuing tool calls never sees the header, so it cannot drop or loosen the filters, and retried calls carry them again.

The header value is base64url(zlib(JSON)) of:

{
  "version": 1,
  "dashboard_id": 12,
  "chart_filters": {
    "101": {"filters": [{"col": "client", "op": "IN", "val": ["A"]}],
            "time_range": "Last quarter"}
  }
}

chart_filters maps each chart with active filters to the extra_form_data the dashboard applies to it. A malformed header refuses every tool call rather than being ignored. Without the header, behavior is unchanged.

While a scope with active filters is present:

  • Chart data tools (get_chart_data, get_chart_preview, get_dashboard_data) apply each chart's dashboard filters and AND any extra_form_data the model supplies with them. Filters can be added but not removed, and time windows, time columns and relative anchors the dashboard sets (including time-series cross-filters) cannot be changed. Charts that are not on the scoped dashboard, and unsaved chart state (form_data_key), are refused.
  • query_dataset, get_table (datasets) and execute_sql apply the filters from dashboard charts backed by the queried dataset, respecting native-filter chart scoping. Datasets outside the dashboard use the combined dashboard-wide filters. A model-supplied time range is intersected with the applicable dashboard time range. execute_sql replaces each filtered table read with a sub-query, the same way row-level security is applied, and refuses SQL whose tables are not registered datasets that have every filtered column, as well as SQL that could read tables it cannot see: opaque statements, functions the SQL parser does not model, and table functions. For execute_sql, template syntax in SQL or dashboard filter values is refused rather than rendered after scoping. For all three tools, the time-filter column is resolved from the affected dashboard charts' temporal filters (or legacy chart time-column settings), after dashboard overrides. The charts must agree on one column. A chart with no temporal target, conflicting targets, or a dataset outside the dashboard with an applicable time window causes a refusal; the dataset's main datetime column and a model-supplied column are never used to guess the dashboard target. Malformed saved chart filter lists also cause an explicit scope refusal before dashboard overrides are merged; no query is run. Without an applicable dashboard time window, no chart temporal target is required, and model-supplied time filtering behaves as before.
  • Writes that change what charts or datasets query (adding a chart to a dashboard, saving a chart, defining a virtual dataset, editing a dataset or metric, restoring a chart or dataset) are refused while the scope is active.
  • Where the filters cannot be applied (for example, a column the dataset lacks, or a column filtered differently by different charts) the call fails with a tool error beginning Dashboard filter scope refused this call:. Tools that return no dataset rows are unaffected; any other tool, including extension tools, is refused.
  • MCP response caching is bypassed for scoped calls, and the scope is applied before any query is built, so Superset's query cache never serves an unscoped result.

The scope is a correctness control for answers, not an access control. Permissions and row-level security apply exactly as they do without it.

Quick Start​

Get the MCP server running locally and connect an AI client in three steps.

1. Start the MCP server​

The MCP server runs as a separate process alongside Superset:

superset mcp run --host 127.0.0.1 --port 5008
FlagDefaultDescription
--host127.0.0.1Host to bind to
--port5008Port to bind to
--debugoffEnable debug logging

The endpoint is available at http://<host>:<port>/mcp.

2. Set a development user​

For local development, tell the MCP server which Superset user to impersonate (the user must already exist in your database):

# superset_config.py
MCP_DEV_USERNAME = "admin"

3. Connect an AI client​

Point your MCP client at the server. For Claude Desktop, edit the config file:

  • macOS: ~/Library/Application Support/Claude/claude_desktop_config.json
  • Windows: %APPDATA%\Claude\claude_desktop_config.json
  • Linux: ~/.config/Claude/claude_desktop_config.json
{
  "mcpServers": {
    "superset": {
      "url": "http://localhost:5008/mcp"
    }
  }
}

Restart Claude Desktop. The hammer icon in the chat bar confirms the connection.

See Connecting AI Clients for Claude Code, Claude Web, ChatGPT, and raw HTTP examples.

Prerequisites​

  • Apache Superset 5.0+ running and accessible
  • Python 3.11+
  • The fastmcp package (pip install fastmcp)

Authentication​

The MCP server supports multiple authentication methods depending on your deployment scenario.

Development Mode (No Auth)​

Disable authentication and use a fixed user:

# superset_config.py
MCP_AUTH_ENABLED = False
MCP_DEV_USERNAME = "admin"

All operations run as the configured user.

warning

Never use development mode in production. Always enable authentication for any internet-facing deployment.

JWT Authentication​

For production, enable JWT-based authentication. The MCP server validates a Bearer token on every request.

Option A: RS256 with JWKS endpoint​

The most common setup for OAuth 2.0 / OIDC providers that publish a JWKS (JSON Web Key Set) endpoint:

# superset_config.py
MCP_AUTH_ENABLED = True
MCP_JWT_ALGORITHM = "RS256"
MCP_JWKS_URI = "https://your-identity-provider.com/.well-known/jwks.json"
MCP_JWT_ISSUER = "https://your-identity-provider.com/"
MCP_JWT_AUDIENCE = "your-superset-instance"

Option B: RS256 with static public key​

Use this when you have a fixed RSA key pair (e.g., self-signed tokens):

# superset_config.py
MCP_AUTH_ENABLED = True
MCP_JWT_ALGORITHM = "RS256"
MCP_JWT_PUBLIC_KEY = """-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA...
-----END PUBLIC KEY-----"""
MCP_JWT_ISSUER = "your-issuer"
MCP_JWT_AUDIENCE = "your-audience"

Option C: HS256 with shared secret​

Use this when both the token issuer and the MCP server share a symmetric secret:

# superset_config.py
MCP_AUTH_ENABLED = True
MCP_JWT_ALGORITHM = "HS256"
MCP_JWT_SECRET = "your-shared-secret-key"
MCP_JWT_ISSUER = "your-issuer"
MCP_JWT_AUDIENCE = "your-audience"
warning

Store MCP_JWT_SECRET securely. Never commit it to version control. Use environment variables:

import os
MCP_JWT_SECRET = os.environ.get("MCP_JWT_SECRET")

JWT claims​

The MCP server validates these standard claims:

ClaimConfig KeyDescription
exp--Expiration time (always validated)
issMCP_JWT_ISSUERToken issuer (optional but recommended)
audMCP_JWT_AUDIENCEToken audience (optional but recommended)
sub--Subject -- primary claim used to resolve the Superset user

User resolution​

After validating the token, the MCP server resolves a Superset username from the claims. It checks these in order, using the first non-empty value:

  1. subject -- the standard sub claim (via the access token object)
  2. client_id -- for machine-to-machine tokens
  3. payload["sub"] -- fallback to raw payload
  4. payload["email"] -- email-based lookup
  5. payload["username"] -- explicit username claim

The resolved value must match a username in the Superset ab_user table.

Scoped access​

Require specific scopes in the JWT to limit what MCP operations a token can perform:

# superset_config.py
MCP_REQUIRED_SCOPES = ["mcp:read", "mcp:write"]

Only tokens that include all required scopes are accepted.

Custom Auth Provider​

For advanced scenarios (e.g., a proprietary auth system), provide a factory function. This takes precedence over all built-in JWT configuration:

# superset_config.py
def my_custom_auth_factory(app):
    """Return a FastMCP auth provider instance."""
    from fastmcp.server.auth.providers.jwt import JWTVerifier
    return JWTVerifier(
        jwks_uri="https://my-auth.example.com/.well-known/jwks.json",
        issuer="https://my-auth.example.com/",
        audience="superset-mcp",
    )

MCP_AUTH_FACTORY = my_custom_auth_factory

Embedded Guest Authentication​

Superset's embedded dashboards feature mints short-lived guest tokens for anonymous/embedded viewers. The MCP server can accept these same guest tokens, so an embedded guest (e.g. an in-app chatbot next to an embedded dashboard) can call MCP tools scoped to the dashboards/resources named in its token.

This is opt-in and reuses the existing core guest-token configuration -- there is no MCP-specific guest secret or audience.

# superset_config.py
FEATURE_FLAGS = {"EMBEDDED_SUPERSET": True}   # required -- guest tokens only exist when this is on
MCP_EMBEDDED_GUEST_AUTH_ENABLED = True        # opt-in for the MCP transport (default False)

Present the guest token the same way as any other bearer token:

curl -X POST http://localhost:5008/mcp \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer YOUR_GUEST_TOKEN' \
  -d '{"jsonrpc": "2.0", "method": "tools/list", "id": 1}'

How it works

  • A dedicated guest-token verifier validates the token against the same GUEST_TOKEN_JWT_SECRET / GUEST_TOKEN_JWT_ALGO / GUEST_TOKEN_JWT_AUDIENCE config used by embedded dashboards, replays the embedded structural checks, and enforces revocation (global version bumps and per-dashboard guest_token_revoked_before cutoffs). It runs before the JWT verifier described above, since guest tokens are signed with a different key/algorithm and would otherwise be rejected at the transport.
  • A verified guest resolves to a Superset guest user as the highest-priority identity, so it's never downgraded to API-key / MCP_DEV_USERNAME / dev-mode resolution. Data access is scoped by the same checks (dataset allowlist, dashboard access, row-level security) that apply to embedded dashboard views.
  • Guests are restricted to a default-deny allow-list, MCP_GUEST_ALLOWED_TOOLS, regardless of MCP_RBAC_ENABLED. Sensitive enumeration tools like find_users and get_instance_info are denied simply by being absent from the default list.
  • Setting MCP_AUTH_FACTORY bypasses this whole path: a configured factory is tried first, and the default factory that wires up the guest-token verifier is never reached. If you rely on a custom auth factory (e.g. your own OIDC provider) alongside guest auth, that factory must verify guest tokens itself -- otherwise they're rejected regardless of MCP_EMBEDDED_GUEST_AUTH_ENABLED.
# superset_config.py
MCP_GUEST_ALLOWED_TOOLS = {
    "get_dashboard_info",
    "get_dashboard_layout",
    "get_dashboard_data",
    "list_dashboards",
    "list_charts",
    "get_chart_info",
    "get_chart_data",
    "get_chart_preview",
}  # default

Deployment requirements

  • The MCP server and the service that mints guest tokens (the Superset web app) must share GUEST_TOKEN_JWT_SECRET and GUEST_TOKEN_JWT_AUDIENCE. Set GUEST_TOKEN_JWT_AUDIENCE explicitly -- if it's unset, audience validation falls back to the URL host, which can differ between the two services and cause every guest token to fail validation.
  • The GUEST_ROLE_NAME role (default Public) must exist -- a guest token is rejected if it does not.
  • Don't set MCP_DEV_USERNAME on a deployment that also serves embedded guests.
  • Restart the MCP process after toggling EMBEDDED_SUPERSET or MCP_EMBEDDED_GUEST_AUTH_ENABLED -- guest auth is wired up once at startup.
warning

GUEST_TOKEN_JWT_SECRET guards both the web embedding and MCP guest-auth surfaces. With MCP_EMBEDDED_GUEST_AUTH_ENABLED on, leaving it at its insecure default isn't just a forgery risk -- the MCP server refuses to start (MCPAuthConfigError) until you set a real secret shared with the guest-token minting service.

Deployment​

Single Process​

The simplest setup: run the MCP server alongside Superset on the same host.

superset_config.py:

MCP_SERVICE_HOST = "0.0.0.0"
MCP_SERVICE_PORT = 5008
MCP_DEV_USERNAME = "admin"  # or enable JWT auth

# If behind a reverse proxy, set the public-facing URL so
# MCP-generated links (chart previews, SQL Lab URLs) resolve correctly:
MCP_SERVICE_URL = "https://superset.example.com"

Start both processes:

# Terminal 1 -- Superset web server
superset run -h 0.0.0.0 -p 8088

# Terminal 2 -- MCP server
superset mcp run --host 0.0.0.0 --port 5008

Nginx reverse proxy with TLS:

server {
    listen 443 ssl;
    server_name superset.example.com;

    ssl_certificate     /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    # Superset web UI
    location / {
        proxy_pass http://127.0.0.1:8088;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # MCP endpoint
    location /mcp {
        proxy_pass http://127.0.0.1:5008/mcp;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header Authorization $http_authorization;
    }
}

Docker Compose​

Run Superset and the MCP server as separate containers sharing the same config:

# docker-compose.yml
services:
  superset:
    image: apache/superset:latest
    ports:
      - '8088:8088'
    volumes:
      - ./superset_config.py:/app/superset_config.py
    environment:
      - SUPERSET_CONFIG_PATH=/app/superset_config.py

  mcp:
    image: apache/superset:latest
    command: ['superset', 'mcp', 'run', '--host', '0.0.0.0', '--port', '5008']
    ports:

Multi-Pod (Kubernetes)​

For high-availability deployments, configure Redis so that replicas share session state:

superset_config.py:

MCP_STORE_CONFIG = {
    "enabled": True,
    "CACHE_REDIS_URL": "redis://redis-host:6379/0",
    "event_store_max_events": 100,
    "event_store_ttl": 3600,
}

When CACHE_REDIS_URL is set, the MCP server uses a Redis-backed EventStore for session management, allowing replicas to share state. Without Redis, each pod manages its own in-memory sessions and stateful MCP interactions may fail when requests hit different replicas.

MCP_STATELESS_HTTP (default True) controls whether requests get a fresh, ephemeral transport per HTTP round trip or a transport that stays alive for the session's lifetime. The default suits multi-pod deployments because it doesn't require session affinity -- any pod can handle any request. Its tradeoff: a client disconnecting mid-tool-call can crash not just its own session but other concurrent sessions on the same worker. Setting it to False avoids that, but it requires session-affinity (sticky session) routing on Mcp-Session-Id at the mesh/ingress layer, since a session's follow-up requests must land on the same pod that created it. See MCP_STATELESS_HTTP below.

Tool discovery modes​

The MCP server can advertise its tools in two ways. Both modes serve the same registered tool definitions through the same middleware, authentication, and permission checks; only the tools/list response differs.

ModeMCP_TOOL_SEARCH_CONFIG["enabled"]tools/list returnsCalling tools
Compatibility (default)TrueThe pinned always_visible tools plus search_tools and call_toolThrough the call_tool proxy, or directly by name
NativeFalseEvery tool the caller may use, under its real nameDirectly by name with tools/call

Every registered tool can be called directly by name in both modes. In native mode each listed tool carries its full description, input schema, and read-only/destructive/idempotent/open-world annotations, plus its output schema when MCP_STRUCTURED_OUTPUT_ENABLED = True. The listing is a single page with no cursor. Schema $ref definitions are inlined on the wire, with nullable unions and constraints preserved, and calls are validated against the same server-side models in either mode.

The native listing is much larger than the compatibility listing, and it grows when structured output is enabled. Per-tool description lengths, schema sizes, and catalog totals for both structured-output settings are recorded in tests/unit_tests/mcp_service/native_tool_inventory.json and enforced by regression tests. Clients and gateways that cap the size of a single list response should be checked against those totals before switching modes.

Authorization in both modes​

  • tools/list in native mode and search_tools in compatibility mode apply the same visibility check: RBAC, token scopes, the restricted-principal tool policy, and data-model metadata access.
  • Each tool enforces the same checks again when it is called, so naming a hidden tool directly, or passing it to call_tool, is rejected with the same error. Revoked permissions take effect on the next request.
  • Tools in ALLOWED_UNPROTECTED (generate_bug_report) intentionally run without authentication for every caller in both modes.
  • When no authentication source is configured at all (development only), native tools/list shows every tool, while search_tools returns only tools without a permission requirement. Protected calls are rejected in both modes until a user can be resolved.
  • call_tool returns the same result as a direct call, including isError, validation details, and structuredContent when structured output is enabled.

Migrating to native mode​

  1. Confirm that every client used with the deployment calls tools by name from tools/list and accepts the size of the full listing. Clients that load tool definitions lazily on their own side work with native mode.
  2. Choose MCP_STRUCTURED_OUTPUT_ENABLED separately; it is independent of the discovery mode.
  3. Set MCP_TOOL_SEARCH_CONFIG["enabled"] = False. To roll back, set it to True; no client or server state needs migrating.

Clients that call tools by name work against servers in either mode. Clients that only know search_tools and call_tool fail against a server in native mode, because those two tools are not served there. Keep compatibility mode until such clients have migrated, and in multi-pod deployments switch every pod together (or keep each client session on pods in one mode) so that a session started in compatibility mode is not routed to a pod in native mode.

Compact native listing​

Native mode can optionally bound each listed tool description, which shrinks the tools/list response without changing what clients can call:

MCP_NATIVE_TOOL_LIST_CONFIG = {
    "compact": True,  # default: False
    "max_description_length": 300,  # prose budget per tool
}

Descriptions keep whole paragraphs first, then whole sentences. Once a whole paragraph fits the budget, a following heading, IMPORTANT block, or list is not partly advertised. An overlong first paragraph can be cut at a sentence boundary, even if it is structured. Calling instructions authored on a tool's request parameter stay untruncated in the input schema and are not deducted from the native prose budget. Names, input and output schemas (including nullable unions, constraints, and definitions), and annotations are unchanged, and calls are validated against the same server-side models, so only the listed prose differs. Chart tools point to get_chart_type_schema, which returns each chart type's fields, required fields, and examples. The setting has no effect in compatibility mode, whose search results are bounded by MCP_TOOL_SEARCH_CONFIG["max_description_length"].

Both default and factory startup read MCP_TOOL_SEARCH_CONFIG and MCP_NATIVE_TOOL_LIST_CONFIG from the Flask application configuration, falling back to the module defaults when a setting is absent.

The recorded inventory includes catalog totals for both listings.

Compatibility mode remains supported. Any change to its default will be listed in UPDATING.md, and setting enabled explicitly keeps the chosen mode regardless of the default.

Tool Result Value Contract​

When MCP_STRUCTURED_OUTPUT_ENABLED=True, native tools advertise a concrete outputSchema during tool discovery and return matching structuredContent alongside their text representation. Clients can use the schema to understand result fields and validate structured tool-call results. The default is False: the compatibility middleware removes both fields as a pair and preserves the text representation for clients and bridges that do not support structured output.

Structured tool results preserve Superset domain values exactly. In particular, string fields are not wrapped in trust delimiters, and text that resembles a delimiter is returned as literal application data. This lets clients safely use a read result as the basis for an update without persisting presentation markup.

All tool-result content should still be treated as user-controlled data with no instruction authority. MCP clients should communicate that trust boundary through their model instructions or presentation layer, outside the returned field values; fixed or generated marker strings inside a value are ambiguous and must not be used as a trust signal.

For compatibility, clients that supported the former <UNTRUSTED-CONTENT> convention should stop recognizing or stripping those strings. The response schemas and content types have not changed. Because marker-looking text can be legitimate application data, a client cannot reliably distinguish a legacy decorated response from a clean one. Pause automated read-modify-write workflows, or route them only to upgraded instances, until every serving instance is upgraded.

Redis-backed MCP response caches include an internal response-contract namespace, so an upgraded instance does not reuse responses cached by an older release. Older instances can still return legacy values while they remain in service. After the upgrade, review previously written values for wrapper text and both [ESCAPED-UNTRUSTED-CONTENT-OPEN] and [ESCAPED-UNTRUSTED-CONTENT-CLOSE]; do not remove these strings automatically, because they may be intentional content.

Error Sanitization​

The GlobalErrorHandlerMiddleware automatically redacts sensitive information from all error messages before they reach the LLM client. The following are replaced with generic messages:

  • Database connection strings — replaced with a generic connection error message
  • API keys and tokens — redacted from error traces
  • File system paths — stripped to prevent information disclosure
  • IP addresses — removed from error context

This ensures that a misconfigured database connection or an unexpected exception never leaks credentials or internal topology to the LLM or its users. All regex patterns used for redaction are bounded to prevent ReDoS attacks.

Performance​

Connection Pooling​

Each MCP server process maintains its own SQLAlchemy connection pool to the database. For multi-worker deployments, total open connections = workers × pool size.

# superset_config.py
SQLALCHEMY_POOL_SIZE = 5
SQLALCHEMY_MAX_OVERFLOW = 10
SQLALCHEMY_POOL_TIMEOUT = 30
SQLALCHEMY_POOL_RECYCLE = 3600  # Recycle connections after 1 hour

For a 3-pod Kubernetes deployment with the defaults above, expect up to 3 × (5 + 10) = 45 connections. Size your database's max_connections accordingly.

Response Caching​

Enable response caching for read-heavy workloads (dashboards/datasets that don't change frequently). With the in-memory backend (default when MCP_STORE_CONFIG is disabled), caching is per-process. Use Redis-backed caching for consistent cache hits across multiple pods:

MCP_CACHE_CONFIG = {
    "enabled": True,
    # Cache keys don't include the requesting principal and hits are served
    # ahead of auth/RBAC, so a shared cache can return one caller's response
    # to another. Required for caching to actually start -- only appropriate
    # when every request is guaranteed to come from the same principal.
    "dangerously_share_cache_across_principals": True,
    "CACHE_KEY_PREFIX": "mcp_cache_",
    "call_tool_ttl": 3600,
}
MCP_STORE_CONFIG = {"enabled": True, "CACHE_REDIS_URL": "redis://redis:6379/0"}

Every tool with a side effect (create/update/delete/execute) is always excluded from caching regardless of this setting -- see the excluded_tools default in superset/mcp_service/mcp_config.py for the current list.

Chart previews​

Saved and unsaved Vega-Lite previews return NoDataError for empty query results unless the chart plugin declares allows_empty_result (for example, Gantt renders an empty task list).

For basic Vega-Lite previews, the y-axis uses the first configured metric whose result label is present and whose first value is numeric or null. Boolean and string metric values are skipped. If metric labels match but none has a suitable value, the y-axis is omitted. Only when no metric label matches does the preview fall back to the first numeric, non-boolean column; aggregation words in column names do not make nonnumeric values eligible.

Troubleshooting​

Server won't start​

  • Verify fastmcp is installed: pip install fastmcp
  • Check that MCP_DEV_USERNAME is set if auth is disabled -- the server requires a user identity
  • Confirm the port is not already in use: lsof -i :5008

401 Unauthorized​

  • Verify your JWT token has not expired (exp claim)
  • Check that MCP_JWT_ISSUER and MCP_JWT_AUDIENCE match the token's iss and aud claims exactly
  • For RS256 with JWKS: confirm the JWKS URI is reachable from the MCP server
  • For RS256 with static key: confirm the public key string includes the BEGIN/END markers
  • For HS256: confirm the secret matches between the token issuer and MCP_JWT_SECRET
  • Enable MCP_JWT_DEBUG_ERRORS = True for detailed server-side logging (errors are never leaked to the client)

Tool not found​

  • Ensure the MCP server and Superset share the same superset_config.py
  • Check server logs at startup -- tool registration errors are logged with the tool name and reason
  • In native mode (MCP_TOOL_SEARCH_CONFIG["enabled"] = False) search_tools and call_tool are not served; call tools by name or re-enable compatibility mode

Client can't connect​

  • Verify the MCP server URL is reachable from the client machine
  • For Claude Desktop: fully quit the app (not just close the window) and restart after config changes
  • For remote access: ensure your firewall and reverse proxy allow traffic to the MCP port
  • Confirm the URL path ends with /mcp (e.g., http://localhost:5008/mcp)

Permission errors on tool calls​

  • The MCP server enforces Superset's RBAC permissions -- the authenticated user must have the required roles
  • In development mode, ensure MCP_DEV_USERNAME maps to a user with appropriate roles (e.g., Admin)
  • Check superset/security/manager.py for the specific permission tuples required by each tool domain (e.g., ("can_execute_sql_query", "SQLLab"))

Response too large​

Two independent limits can reject a large result. Check the error type to tell them apart:

  • Response size guard (configurable). An error about exceeding the response size limit comes from ResponseSizeGuardMiddleware, which measures the serialized tool response.
    • Reduce page_size or limit parameters, use select_columns to exclude large fields, or add filters to narrow results
    • To adjust the threshold, change max_bytes in MCP_RESPONSE_SIZE_CONFIG
    • To disable the guard entirely, set MCP_RESPONSE_SIZE_CONFIG = {"enabled": False}
  • Chart query result limits (mandatory). An InvalidQueryResult error such as "Chart query returned too many rows" or "hostile or oversized row data" comes from validation of the chart query result itself, before any response is built. These limits are fixed safety bounds and are not affected by MCP_RESPONSE_SIZE_CONFIG; raising max_bytes or disabling the guard does not change them. They cap a result at 50,000 rows per query and 100,000 rows in total, 4,096 columns, 2,500,000 values, 16 MiB of JSON, and 65,536 UTF-8 bytes per text cell (binary cells are bounded by the same per-cell limit). To resolve them, reduce the chart's row limit, add filters, select fewer or narrower columns, or aggregate the data.

Audit Events​

All MCP tool calls are logged to Superset's event logger, the same system used by the web UI (viewable at Settings → Action Log). Each event captures:

  • Action: mcp.<tool_name>.<phase> (e.g., mcp.list_databases.query)
  • User: the resolved Superset username from the JWT or dev config
  • Timestamp: when the operation ran

This means MCP activity is auditable alongside normal user activity. No additional configuration is required — logging is on by default whenever the event logger is enabled in your Superset deployment.

Tool Metrics​

The configured stats logger records one outcome counter (mcp.tool.<tool_name>.success, .warning, or .error) and one timing (mcp.tool.<tool_name>.time) per tool execution. Calls forwarded through the tool-search proxy, including a custom call_tool_name, use the target tool's metrics without a second counter or timing from the proxy. This applies to both successful and failed calls; exceptions raised by the proxy itself are still counted.

Tool Pagination​

MCP list tools (list_datasets, list_charts, list_dashboards, list_databases) use offset pagination via page (1-based) and page_size parameters. Responses include page, page_size, total_count, total_pages, has_previous, and has_next. To iterate through all results:

# Example: fetch all charts across pages
all_charts = []
page = 1
while True:
    result = mcp.list_charts(page=page, page_size=50)
    all_charts.extend(result["charts"])
    if not result.get("has_next"):
        break
    page += 1

Asset Catalog​

get_catalog returns a compact catalog page for one asset type (databases, datasets, charts, or dashboards). It is designed for assistants that need an inventory of what a user can see without calling the full list tools repeatedly:

  • Per-user and live: every call reads through the same DAO visibility filters as the matching list tool, as the calling user. Nothing is cached or stored, and the tool is always excluded from MCP response caching, so a revoked grant is reflected on the next call. This also applies through the tool-search call_tool proxy (including a custom call_tool_name): proxy responses are never cached, leaving cache policy to the target tool.
  • Field allowlist: each item has only id, uuid, name, description, changed_on, and url. SQL, extra, template parameters, metric expressions, and connection details are never read or returned.
  • Restricted marker: users without data-model metadata access receive restricted: true with no items for databases and datasets.
  • Bounded: page_size is at most 100, and each response stays under 32 KiB. Pages use an opaque keyset next_cursor, bound to the asset type and search term, that stays stable when assets are added or removed between pages. truncated: true means the page ended early to fit the size bound, or a long name or description was shortened.
page = mcp.get_catalog(request={"asset_type": "dashboards", "page_size": 50})
while page["next_cursor"]:
    page = mcp.get_catalog(
        request={"asset_type": "dashboards", "cursor": page["next_cursor"]}
    )

Chart datasource metadata​

For roles allowed to view data-model metadata, get_chart_info includes datasource_id in its default columns. Dashboard chart summaries include datasource_type alongside datasource_id, which is only unique within its type. Both fields are redacted for users without data-model metadata access. Chart and dashboard chart summaries resolve dataset names from the live table or semantic view, so renames are reflected without resaving the chart. Query and saved-query charts retain their stored datasource names; missing tables or semantic views do not fall back to stale names. Saved-chart get_chart_data and get_chart_info prechecks, and the chart access checks in add_chart_to_existing_dashboard, generate_dashboard, and update_chart, resolve semantic-view sources by type and ID, then check access before continuing. update_chart then refuses semantic-view charts, which it cannot yet edit. SQL-dataset charts retain their existing dataset validation.

list_charts filters on datasource_name use these same live names before pagination and counting. For tables with a schema, filter using schema.table_name. Data-model metadata permission checks also apply to these filters and returned identifiers.

Trash Listing (Soft-Deleted Objects)​

When the SOFT_DELETE feature flag is enabled, deleting a chart or dashboard moves it to trash rather than removing it outright. The list_charts and list_dashboards tools accept a deleted_state parameter to surface those trashed objects:

  • deleted_state="only" — return only trashed objects
  • deleted_state="include" — return live and trashed objects together
  • Omitted (default) — live objects only; trashed objects are excluded
# List only trashed charts
result = mcp.list_charts(request={"deleted_state": "only"})

Trashed rows carry a non-null deleted_at timestamp in the response (populated only when deleted_state is used). Visibility follows the same restore-audience scoping as the equivalent REST API filters (chart_deleted_state / dashboard_deleted_state): a non-admin caller sees only the trashed objects they can edit (the same audience that can restore them), not merely the ones they own; admins see all trashed objects. That scoping is narrower than the true restore audience in two cases it can't express in SQL: editorship granted via EXTRA_EDITORS_RESOLVER and guest users whose editorship derives from roles. Callers in either case may be able to restore a trashed object via POST /restore yet not see it listed here.

deleted_state is only defined on list_charts and list_dashboards. Other list tools don't declare the field at all, so passing it is silently ignored rather than rejected — it never returns trashed objects.

Disabling built-in tools​

If you have deployed a custom tool via a Superset extension that supersedes one of the built-in Superset tools, you can suppress the built-in version so AI clients only discover your replacement. Disabled tools are removed from the server at startup and are never advertised during tool discovery.

Set MCP_DISABLED_TOOLS in your superset_config.py to a set of tool names:

# superset_config.py

# Disable one tool
MCP_DISABLED_TOOLS = {"execute_sql"}

# Disable multiple tools
MCP_DISABLED_TOOLS = {"execute_sql", "health_check"}

Tool names match the function name used in the @tool decorator (e.g., execute_sql, list_charts, health_check). Extension-prefixed tools can also be disabled using their full prefixed name:

MCP_DISABLED_TOOLS = {"extensions.myorg.myextension.some_tool"}
note

Specifying a tool name that does not exist logs a warning at startup and is otherwise ignored — it will not prevent the server from starting.

Disabling chart type plugins​

The generate_chart tool dispatches per chart type (xy, table, pie, gauge, treemap_v2, pivot_table, interactive_pivot, mixed_timeseries, handlebars, big_number, histogram, box_plot, waterfall) to a registered chart type plugin. Gauge requests use the public MCP discriminator chart_type: "gauge"; Superset stores the corresponding native Explore visualization as viz_type: "gauge_chart". Two settings let operators enable or disable individual chart type plugins at runtime, without a code deploy.

Saved Bubble and Histogram Vega-Lite previews with zero rows return an empty specification instead of NoDataError, matching their unsaved previews.

Gauge data inspection and JSON/CSV/XLSX exports preserve source groups using the same row-count and completeness semantics as other chart types. Shared result normalization converts non-finite floats to null before export: JSON returns null, and CSV and both XLSX writers produce blank cells. These values are indistinguishable from SQL NULL; exports do not retain nan, inf, or -inf text. An overflowing aggregate can therefore appear as a missing value. Only previews and compile checks skip NULL, NaN, non-finite, and other nonnumeric dial values while preserving finite groups. In preview/compile paths, a nonempty result containing no finite dial returns an error; genuinely empty results retain the no-data behavior. Compile checks inspect the configured dial limit (at most 10), rather than only two groups. Grouped Vega previews center each needle within its own facet and extend it to the midpoint of the dial band. Automatic all-zero ranges span 0–1. Empty or whitespace-only temporal ranges, like No filter, are neutral sentinels; missing or non-string native temporal comparators are invalid.

Gauge previews retain data-derived automatic bounds even when configured interval thresholds extend beyond the visible range; Vega previews clip those thresholds into adjacent, non-overlapping bands. Explicit min/max bounds still constrain intervals. All-zero data with both bounds omitted uses a nondegenerate preview range of 0–1. On same-dataset Gauge updates, clearing or changing the dashboard temporal binding preserves user-authored temporal ranges; dataset rebinds discard old query roles and filters. The native "No filter" sentinel is a neutral dashboard temporal binding, not a conflicting restriction. Duplicate generated neutral bindings self-heal on updates without removing user-authored ranges. Restating the existing dataset ID without a config is allowed; changing the Gauge dataset still requires a complete config. Native restrictive temporal filters that conflict with the top-level range or another restrictive temporal filter are rejected rather than silently dropped. Unsupported native filter operators are rejected with an indexed error. Native TEMPORAL_RANGE adhoc filters require an explicit string comparator; "No filter", empty strings, and whitespace represent an unrestricted range.

Static deny-list​

Set MCP_DISABLED_CHART_PLUGINS in your superset_config.py to a set of chart type names:

# superset_config.py

# Emergency kill switch: hide "handlebars" from all callers

Dynamic predicate​

For per-request control (A/B tests, gradual rollout, entitlement checks), set MCP_CHART_PLUGIN_ENABLED_FUNC to a callable. It's evaluated as enabled_func(chart_type: str) -> bool on every registry lookup, and it takes precedence over MCP_DISABLED_CHART_PLUGINS when set:

# superset_config.py
from flask import g


def MCP_CHART_PLUGIN_ENABLED_FUNC(chart_type: str) -> bool:
    flags = getattr(g, "feature_flags", {})
    return flags.get(f"mcp_chart_{chart_type}", True)

The callable must be cheap and in-process (consult already-loaded feature flags or request-local context) -- do not perform network I/O per call. If it raises, the registry fails closed (the plugin is hidden) and logs a warning.

Disabling a plugin only stops new charts of that type from being created. Existing saved charts of that type keep their plugin's query, result-validation and preview behavior in get_chart_data, get_chart_preview and get_chart_sql. Updates through update_chart and update_chart_preview also retain the plugin's configuration completion, column validation, merge rules, and compile checks. Gauge and Treemap compile checks use a safe 10-row fallback for malformed (including boolean) or nonpositive saved row limits. Malformed Gantt query fields return a validation error rather than a generic data-retrieval error. Funnel Vega-Lite previews return InvalidFormData when a stage reference has no resolvable result label. Mixed timeseries queries keep each axis's series grouping separate from the time-axis column. Saved charts with a scalar groupby retain the full column name in Waterfall queries and Funnel/Histogram Vega-Lite previews.

Saved Histogram and Gantt charts apply time_range to the date column selected by granularity_sqla. A normalized granularity override takes precedence, including an explicit clear.

Reporting query dates​

query_dataset and get_table return from_dttm (inclusive) and to_dttm (exclusive): the primary time boundaries from the query engine's result payload, including cached and empty results. Callers should quote these ISO 8601 values when explaining the numbers, rather than calculate dates from the request again. For example, previous calendar month evaluated on July 17, 2026 resolves to 2026-06-01T00:00:00 through, but not including, 2026-07-01T00:00:00. Last month is a rolling month, not the previous calendar month.

On a cache hit, these bounds reflect the current request, not necessarily the original cached execution. A cached result can outlive a relative-range rollover; check cache_status.cache_hit before describing the bounds as execution dates.

Relative expressions use Superset's server clock and configured DEFAULT_RELATIVE_START_TIME / DEFAULT_RELATIVE_END_TIME (both default to today, meaning midnight). Valid explicit dates are used as supplied; the server cannot determine whether a model intended a different year.

These fields describe the engine's primary logical range, not the observed minimum/maximum dates in the rows or every SQL predicate. A null boundary means no primary bound is available; it does not prove the absence of other filters. Additional column filters and virtual dataset SQL can further constrain the data. MCP validation rejects open-ended time_range strings such as "2025-01-01 : " or " : 2025-02-01" before execution; use explicit comparison filters for one-sided constraints. Those comparisons are not primary bounds. Naive boundaries are not labeled UTC: dataset timezone or legacy hour-offset settings can adjust the SQL comparisons. Use the applied filters and datasource settings as well when explaining such queries. query_dataset.applied_filters retains the original expressions so callers can compare the requested and resolved ranges.

Overriding a saved chart's time grain​

Pass extra_form_data={"time_grain_sqla": "P1M"} to get_chart_data or get_chart_sql to aggregate a saved chart by month instead of its saved grain. For Generic Chart Axes charts, both MCP overrides and dashboard time-grain filters update the BASE_AXIS column's timeGrain, regardless of its position in the query's columns list. Other columns are left untouched. Queries without a BASE_AXIS column continue to use extras.time_grain_sqla. Same-visualization updates that supply only a non-null time_grain preserve saved temporal range filters. Explicitly setting time_grain to null clears saved temporal state, including time_range and temporal range filters; it does not preserve the date restriction. Supply time_range or temporal_column to change the temporal restriction or binding.

Exploring large dashboard layouts​

get_dashboard_layout returns the full parsed layout by default. For large dashboards, pass tabs_only=true to retrieve just the tab tree in tab_tree: id, name (the title), parent_tab_id, zero-based depth, and chart_count (distinct charts in the tab and its descendants). In this mode tabs and charts are empty by request, not because the dashboard is empty. Then pass tab="<ID or exact title>" to retrieve that tab and its descendants with chart positions. Matching is case-sensitive; IDs take precedence and ambiguous titles require an ID. Both options can be combined to summarize a subtree. Parent IDs, depths, and chart paths retain their full-dashboard context.

Charts placed outside every tab are counted in untabbed_chart_count in every response; pass untabbed_only=true (without tab or tabs_only) to list only those charts. The scope field echoes the applied tabs_only, resolved tab_id, and untabbed_only values, and is null for the full layout. Scoping only removes tabs and chart placements from the layout the caller can already retrieve. Conflicting scope options return an actionable invalid_scope error naming the options to remove; blank tab selectors return tab_not_found rather than widening the scope. On dashboards without tabs, tabs_only=true returns tab_not_found with guidance to use untabbed_only=true or request the full layout instead.

Permalink active-tab and filter state remain unchanged; only an explicit tab scopes the response. Oversized layout errors suggest the next narrower scope: the tab tree and untabbed charts for a full tabbed layout, a top-level tab for an oversized tab tree, a nested tab for a tab that has one, and list_charts paging when a dashboard without tabs or a tab without nested tabs is still too large.

Reading applied dashboard filters​

When answering about a filtered dashboard, call get_dashboard_info with the dashboard's permalink_key (a saved snapshot) or caller-supplied filter_state. This value projection is provided by get_dashboard_info; get_dashboard_layout retains its existing metadata-redacted layout state and does not return native filter values. The tool cannot observe browser state without one of these inputs. Its response includes filter_state by default; an explicit select_columns must include it.

For users without Dataset drill/write metadata permissions, including embedded guests, raw dataMask and chartStates remain hidden. Instead, filter_state.native_filter_values contains configured native filter IDs, display names, types, and scalar or flat-list selections for select, numeric range, time range, and time-grain filters, plus display labels and exclusion flags when present. It does not expose filter targets, dataset IDs, columns from query metadata, or arbitrary nested filter state. Time-column filters, custom filters, unknown IDs, and chart cross-filter state are not projected. Historical masks containing time-column metadata are also omitted, even if the configured filter type has changed; malformed type-specific value shapes are omitted rather than interpreted. native_filter_values_incomplete flags omitted or malformed context, including SQL or wildcard predicates that cannot be represented by selected values alone. It also flags retained selections without query predicates (for example, a cleared or not-yet-applied mask). These display values are not proof that a predicate is active.

These values describe a snapshot, not automatically enforced query predicates or a complete account of filter scope. An empty or missing summary must not be treated as permission to query unfiltered or workspace-wide data. Respect chart scope and ask for clarification when the context cannot safely constrain an answer. Dashboard access checks and row-level security remain independent of this display-context projection. Integrations must ensure the lookup actually happens and the assistant uses the result; tool guidance alone cannot guarantee this.

Tool-call errors​

For exceptions raised by tools, the shared error handler distinguishes permission denials, invalid arguments, datasource failures, invalid SQL, and internal errors. Datasource responses include an enumerated reason rather than raw driver output; internal errors return an error ID rather than implementation details. Tools such as get_chart_data that return structured error envelopes instead of raising do not pass through this handler.

Missing tables, columns, and schemas log at WARNING without invoking MCP_ERROR_HOOK, even when the exception inherits status 500. Connection failures with status 500 or higher remain ERROR and invoke the hook. An explicitly sub-500 exception remains a warning even if it carries a connection error reason: the generic engine reason can also describe a caller's malformed column, and a connection access denial is still a permission failure.

The error hook runs off the transport loop in its own application and metadata session scope, without reloading the request user. Reporting an error therefore does not require metadata database access unless the hook itself uses it. Use the provided hook context for caller identity rather than g.user.

SQL execution row limits​

The execute_sql tool treats an explicit request limit as a safety cap on the last statement's outer SQL LIMIT. The smaller limit wins: SQL LIMIT 5 with request limit: 10 returns at most five rows, while SQL LIMIT 10 with request limit: 5 also returns at most five. Equal limits and SQL LIMIT 0 are preserved. If SQL has no outer limit, the explicit request cap is applied. Inner query and CTE limits and SQL offsets are preserved. Literal FETCH FIRST counts and parenthesized literal limits follow the same rule. PERCENT, WITH TIES, and limit expressions that cannot be interpreted as a fixed row count are preserved inside a subquery with an outer row cap, rather than replaced. This conservative fallback cannot increase the original result's row count. For SQL Server, these restrictions are left unchanged instead: a derived table could reject duplicate or unnamed output columns. The executor caps the last statement's returned rows at the smaller of the explicit request limit and SQL_MAX_ROW, without changing percentage, tie, or expression semantics. Cursor reads are bounded by the same cap plus one probe row, including across multiple fetch batches, preserving engine-specific result processing. Only successfully returned rows count against the cursor budget, so a failed fetch leaves that budget available for an engine fallback. BigQuery only falls back if its initial fetch fails; errors after a successful sample, including during the EOF probe, fail the query rather than silently discarding buffered rows. This does not bound the work performed by the database. Because this cap applies to any row-returning last statement, a non-query statement such as SHOW TABLES or DML with RETURNING can also be capped. Each statement reports truncated: true when a fetch cap omits rows from the executed SQL result, including engine memory caps such as BQ_FETCH_MAX_MB. Exactly-at-cap and smaller results report false when no rows are omitted. This flag does not indicate rows excluded by a SQL LIMIT visible in executed_sql, and does not bound or count affected rows for a write with RETURNING. In dry_run, the SQL Server restriction remains unchanged because no results are fetched.

Omitting limit leaves the SQL limit unchanged. Explicit request caps remain subject to the server's SQL_MAX_ROW configuration. This behavior also applies to dry_run, which returns the transformed SQL without executing it.

The SQL-only Database.apply_limit_to_sql() helper used by dataset column discovery and alerts does not use the executor's bounded cursor. It retains the legacy SQL Server behavior of replacing PERCENT, WITH TIES, and non-fixed limit expressions with a fixed TOP cap, without introducing derived tables that could reject unnamed or duplicate columns. Smaller fixed limits, including zero, are preserved unless the caller explicitly requests force=True. This legacy helper's replacement semantics are separate from MCP execution's preservation of complex SQL restrictions.

Result serialization​

Data-bearing tool responses sanitize row values, column samples, and statistics. Tuple-valued cells and NumPy arrays (including arrays materialized by Arrow) are returned as JSON arrays. Nested values share the same depth, item, and byte limits as list-valued cells; unsupported containers and subclasses are rejected. Nested maps stringify exact built-in string, integer, float, boolean, and null keys within the key-size budget; arbitrary key objects and subclasses are rejected. Missing and non-finite floating-point values become JSON null; non-UTF-8 binary values become base64 strings prefixed with base64:. Boolean row counts are treated as unavailable, producing null for nullable counts and 0 for non-nullable counts, rather than being interpreted as one or zero rows. Concrete psycopg2 and psycopg PostgreSQL ranges, including ranges nested in array cells, become bounded driver-style text (for example, "[1, 10)"). Range subclasses and unsupported or oversized endpoints are rejected; arbitrary objects are not stringified. Finite SQL Decimal values retain their precision during chart validation and CSV export, but use the existing JSON number format in rows, query results, column samples, and statistics. As with other floating-point JSON numbers, clients should not rely on exact decimal precision in that projection.

Rebuilt get_chart_data queries retrieve the requested row limit rather than a saved Table's server-pagination page size. CSV and Excel exports are not restricted to the first Explore page, and explicit limits apply before execution. Same-visualization Bubble updates preserve omitted series, row_limit, and color_scheme; series: null explicitly removes grouping. Saved Mixed Timeseries Vega-Lite previews honor the requested width and height. Both Mixed Timeseries queries validate SIMPLE filter clauses and column references; unsupported SIMPLE HAVING filters are rejected rather than silently discarded. Same-visualization Mixed Timeseries updates preserve omitted secondary-query controls, including time range, row limits, time grain, rolling/resample settings, and saved or adhoc ranking metrics. New typed Mixed Timeseries charts default secondary grouping to empty rather than inheriting primary grouping. Omitted primary and secondary grouping on updates retain their saved values; group_by: []/null and group_by_secondary: []/null clear only that query's grouping. Explicit secondary controls and clears replace the saved values. Same-visualization aggregate Table updates preserve native percent-metric columns; raw-mode updates, visualization changes, and dataset rebinds do not carry them over. Same-visualization Table updates preserve saved ordering when sort_by is omitted; sort_by: [] clears it. Same-visualization XY updates preserve saved series grouping when group_by is omitted; group_by: [] clears it. Omitted series_limit_metric and timeseries_limit_metric preserve saved series ranking. Either spelling replaces the saved ranking when supplied; null clears it. Native XY BASE_AXIS SQL x-axis objects carry their timeGrain into the chart's time_grain unless a panel-level time_grain or time_grain_sqla is supplied. Table compile and preview row caps take precedence over saved row limits; server pagination can reduce a cap only when its page size is positive. Grouped Mixed Timeseries Vega-Lite previews fold all flattened series columns, so every primary-query group remains visible rather than only the first numeric column. Saved Big Number axes using column_name mappings retain time-range bindings and time-grain bucketing like string axes. Sort-only Timeseries metrics retain their raw values when displayed metrics undergo rolling or cumulative processing. Timeseries compile checks skip rolling windows and forecasting on their bounded two-row sample; full previews and data queries still apply those analytics, so compile success does not validate their full-history behavior.

If a successful generate_chart or update_chart write produces response content beyond serialization limits, the response retains success: true and the saved chart.id, with a warning and optional content omitted. Retrieve the chart by that ID instead of retrying the write. Unsaved responses that exceed these limits still return a structured failure.

Chart data column counts​

For saved and unsaved charts, get_chart_data column metadata excludes missing values from unique_count. Values serialized as JSON null, including NaN, NaT, and non-finite numbers, contribute to null_count instead.

Country and world maps edited in Explore can use Custom SQL entities; MCP reads and exports resolve the saved entity's output label (or SQL expression). Source values remain intact for data/export and country-map cross-filtering. Database NUMERIC/Decimal query coordinates and metrics are supported when finite and representable as JSON numbers. Coordinate bounds are checked before JSON conversion; numeric strings and booleans are not accepted as coordinates.

Generation validates the configured result (up to row_limit, bounded at 10,000), not just the first two rows. This is not an audit of rows excluded by filters or limits. Saved and cached-preview updates preserve omitted controls; explicit null optional roles and empty filters clear them. Native saved maps with null adhoc_filters are treated as having no filters. Preserved numeric-string point radii (for example, "100") render as fixed sizes, not metric names. Dataset rebinding requires a complete typed config and discards old dataset roles and filters.

Geographic updates cap inherited native row limits at 10,000 so compilation validates the same rows the native query renders. Explicit temporal_column: null removes generated dashboard time bindings, including dataset defaults, while preserving user-authored predicates. Subsequent same-dataset updates that omit temporal_column preserve that cleared state. Explicit filters replace inherited predicates, including native filters, where, and having, whether the replacement list is empty or nonempty. Disabled types cannot be used for fresh previews or type conversions; an existing cached preview or saved chart of the same type can still be updated, including charts whose visualization type is stored only on the saved chart. Explicit temporal changes override inherited native time controls on same-type updates and type conversions. Saved point charts switched in Explore to Geohash or comma-delimited coordinates remain readable through MCP data and JSON/CSV/Excel exports; exports retain the original spatial column values. Delimited coordinates accept the same leading numeric prefixes as the native decoder (for example, -122.4 W,37.8 N). Values the native decoder skips still fail MCP result validation, consistent with invalid latitude/longitude and geohash values.

Country/world map interactions use original source identifiers rather than normalized rendering codes or names. With an explicit region format, boundaries absent from the result do not emit cross-filters or drill filters. Empty country identifiers are rejected rather than matched to a country with no code.

ASCII/table previews show source data and do not reproduce geography. Vega previews return UnsupportedGeographicPreview rather than an unrelated chart. Use the returned Explore link for the native map. Point maps use a public Carto basemap; browser network access and deployment basemap policy still apply.

Big Number headlines​

For Big Number charts (big_number and big_number_total), get_chart_data and get_dashboard_data return a headline object holding the number the chart displays. Agents should report headline.value rather than reading or summing the data rows: for the trendline variant the rows are a time series, and the displayed number is derived from the whole series by the chart's aggregation.

FieldContents
valueThe displayed number, or null when it cannot be computed exactly
aggregationtotal for big_number_total; otherwise the chart's aggregation (LAST_VALUE, sum, mean, min, max, median, or raw)
rows_usedThe number of non-null values aggregated
reasonWhy value is null

A headline is only returned when it matches the rendered chart, so value is null with a reason when:

  • The query returned no rows, the metric column is missing, or every metric value is null.
  • The chart applies a rolling window or resampling that the executed query did not include, or the fetch was truncated at the row limit.
  • The aggregation picks the latest value (LAST_VALUE) and some rows have no usable timestamp. The chart's ordering of such rows depends on row order, so the value it shows cannot be determined exactly. Order-independent aggregations still include those rows.
  • The aggregation is raw ("Overall value") and the chart has no saved query context. That value comes from a second query that only a saved query context carries, so unsaved and form_data_key requests return null.

When form_data_key is supplied, the headline follows the unsaved visualization type, including when switching to or from a Big Number chart.

Dataset query dimensions and nested fields​

The query_dataset tool accepts exact column names registered on the selected Superset dataset. Use get_dataset_info with the same dataset_id to discover those names; a column available on one dataset may not exist on another.

A dotted name such as address.city.name can be used as a GROUP BY column when that exact name is registered. Registering only the parent address column does not register its nested fields. If a field is missing, refresh the dataset columns when the database exposes nested-field metadata, or add a calculated column with the warehouse-appropriate field-access expression and query its registered name. For ad-hoc expressions, use execute_sql instead.

Unknown dimensions return the selected dataset's name and ID, up to ten available column names, and a pointer to get_dataset_info for the full list. Unregistered dotted dimensions also include shared nested-field setup guidance once, even when multiple dimensions are missing. The tool does not rewrite dots into SQL path separators: quoting and nested-field support depend on the dataset's database dialect, and dots can also be literal characters in column names.

Treemap charts​

Saved and cached previews honor the configured Treemap row limit across ASCII, table, and Vega representations. SQL Decimal metrics are accepted when finite; booleans and nonfinite values are rejected. Categories with identical display names but distinct raw types retain separate geometry groups. Currency settings use the native symbolPosition property. Adding filters while omitting the temporal column preserves saved predicates and the existing neutral time binding; explicit empty filters or a cleared temporal column remove those controls.

Use chart_type: "treemap_v2" with an ordered groupby hierarchy and one metric. Hierarchy columns accept typed references ({"name": "region"}) or native strings. Metrics accept typed column references with an aggregate, saved metric names, or native SIMPLE/SQL metric objects. SQL metrics still require a label and pass the shared SQL-expression validation. Unknown controls and executable JavaScript hooks are not accepted.

{
  "dataset_id": 7,
  "config": {
    "chart_type": "treemap_v2",
    "groupby": ["region", "product"],
    "metric": {"name": "revenue", "aggregate": "SUM"},
    "row_limit": 100,
    "sort_by_metric": true,
    "show_labels": true,
    "show_upper_labels": true,
    "label_type": "key_value",
    "number_format": ",.2f"
  }
}

Bounded queries sort by the metric descending when requested, then by hierarchy columns ascending to break ties, matching the frontend query contract. update_chart and update_chart_preview preserve omitted same-dataset Treemap controls, including hierarchy, metrics, formatting, filters, temporal state and template_params. Partial configurations are accepted only for updates; a new chart still requires hierarchy and metric roles. Explicit empty filters clear filters, and explicit null clears nullable controls. Rebinding to another dataset requires complete roles and inherits only supported presentation controls.

ASCII and table previews show hierarchy and values. Vega-Lite previews use bounded slice-and-dice rectangles with metric-proportional areas, hierarchy paths, categorical colors, labels and tooltips. This is not the native ECharts layout: use the Explore URL for native formatting and interactions. The preview supports up to 1,000 nonnegative rows, 20 hierarchy levels, and the built-in supersetColors and lyftColors schemes. Unsupported color/currency formats, negative values, zero totals and over-limit geometry return UnsupportedTreemapPreview rather than a substitute scatter or bar chart. SMART_NUMBER is approximated with SI formatting in this preview.

Queries must return every hierarchy output and the metric's exact output label. Malformed/error envelopes and nonnumeric or nonfinite metric outputs return structured errors instead of apparently successful previews, charts or exports.

Dataset discovery and routing​

list_datasets, get_dataset_info, update_dataset, and query_dataset operate on registered SQL datasets (physical tables or virtual SQL queries), not external semantic views. create_dataset registers a physical table as a SQL dataset; it does not create or register semantic views. The certified filter in list_datasets selects certified SQL datasets, not external views.

For existing semantic views, use list_metrics to discover metrics and get_table to query them, retaining the returned source and view identity. These tools do not provision or edit semantic views. A dataset not-found error offers this routing guidance without establishing whether a semantic view exists or is accessible. Numeric IDs can overlap across source types; do not reuse a semantic-view ID as a SQL-dataset ID or substitute another source. All tool permissions, feature flags, and datasource access checks still apply.

list_datasets searches table name, description, schema, and SQL using escaped, case-insensitive substring matching. Write descriptions with business terminology to make differently named datasets discoverable. A complete UUID passed as search is treated as an exact UUID filter; an explicit uuid filter can also look up one or more datasets by UUID. Matching datasets are candidates, ordered by the requested sort (last modified by default), not ranked recommendations. Compare descriptions and metrics, present alternatives when ambiguous, and clarify before querying. No matches does not prove that data does not exist; search only covers accessible datasets and the configured scope.

query_dataset returns dataset_id and dataset_name; get_table additionally returns source and the corresponding dataset or external-view identity. Cite these fields in answers rather than guessing the source from the query text. Neither tool selects an alternative dataset automatically.

Optional per-role dataset scope​

Set MCP_DATASET_ROLE_ALLOWLIST in superset_config.py to constrain MCP to a curated set of registered datasets:

MCP_DATASET_ROLE_ALLOWLIST = {
    "Finance Readers": ["00000000-0000-0000-0000-000000000001"],
    "Operations Readers": ["00000000-0000-0000-0000-000000000002"],
}

Obtain dataset UUIDs from get_dataset_info (or request uuid in list_datasets.select_columns). Use UUIDs, not names or numeric IDs, in config. Effective roles, including group roles, contribute the union of their lists. That union is intersected with existing dataset access. Unconfigured roles contribute nothing; Admin has no routing exemption. None (the default) disables this feature; {} allows no datasets. Invalid entries cause a configuration error at startup rather than silently disabling the restriction.

Scoped mode supports the dataset tools that name a registered dataset — list_datasets, get_dataset_info, query_dataset, and, with a built-in dataset, get_table, list_metrics, get_compatible_dimensions and get_compatible_metrics — plus health_check and get_schema. Discovery filters before counting and pagination. Every other authenticated tool refuses in this mode, including SQL Lab, chart/dashboard previews and data, cached query results, external semantic sources, mutations, and extension tools. The one exception is generate_bug_report, which is deliberately public (protect=False, listed in ALLOWED_UNPROTECTED) so diagnostics stay available even when authentication is broken. Scoped mode is enforced in the authentication wrapper, so that tool keeps working; it reports environment and user-supplied diagnostics and reads no dataset rows. These paths cannot all be attributed reliably to registered dataset UUIDs; scoped mode deliberately refuses them instead of attempting SQL lineage inference. Unsupported tools stay listed and refuse when called, so the assistant reads an explanation it can pass on rather than finding the tool missing. Prompts and resources are unaffected: they expose schema and instance metadata, not dataset rows. This restriction applies to every caller of the MCP tools, not just a particular chat client.

The default MCP_GUEST_ALLOWED_TOOLS contains only chart/dashboard tools, none of which supports dataset-scoped mode. Enabling this allowlist therefore also makes all of those embedded-guest tool calls refuse.

An out-of-scope request returns an explicit refusal. The assistant must explain that limitation, never silently substitute an allowed but different dataset. This feature controls routing and usability, not authorization or SQL table access. Existing dataset permissions, query validation, and row-level security remain mandatory and unchanged. A registered virtual dataset may itself query multiple physical tables; this configuration selects registered dataset objects, not their underlying SQL dependencies. It does not restrict the Superset UI/API.

Description search adds one text predicate to an existing catalog substring scan, without joins or additional queries, and replaces the uuid substring predicate, whose behavior varied by database. It is not an indexed full-text search: large catalogs and long descriptions can increase scan time. Benchmark with your metadata database and catalog size when tuning discovery latency.

Managing and applying dashboard native filters​

manage_native_filters requires a numeric dataset column when adding a filter_range filter or changing its dataset/column target. Select filters continue to accept nonnumeric columns.

Dividers are visual separators and are always in scope. When updating a divider with manage_native_filters, use name to change its title and description to change its description; scope_chart_ids is rejected. apply_dashboard_filters excludes dividers from its available-filter error lists.

For apply_dashboard_filters, pass time_grain as a list containing at most one datasource-supported duration (for example, ["P1D"]). Custom engine durations are accepted when exposed in the datasource's time-grain options, rather than limited to a fixed enum. A nonempty time_grains list in the saved filter configuration restricts the allowed selection to grains that appear in both that list and the target dataset's supported time grains; missing or empty lists use the dataset's supported grains. Pass [] to clear an optional time-grain filter; required filters cannot be cleared.

Missing chart columns​

generate_chart, update_chart, update_chart_preview and generate_explore_link all validate column references through validate_and_compile and return the same structured errors.

A reference to a missing column returns column_not_found with up to three similar physical column names ("Did you mean: ..."), or explicit no-match guidance when nothing is close enough. Saved metrics — both names and expressions — are excluded from these candidates for dimension and WHERE references, because only a physical column is legal there and suggesting a metric leads to invalid SUM(metric) SQL. SIMPLE HAVING filters are unsupported, so their column errors do not suggest saved metrics either. When a reference in a metric slot (y, metric, Sunburst secondary_metric, or an aggregated table column, for example) near-misses a saved metric name, the error adds a hint to reference it as {"name": "<metric>", "saved_metric": true} instead. Dimension references never receive this hint, even when they carry an aggregate.

When more than one distinct column is missing, the error type is multiple_invalid_columns. The invalid names appear in escaped, length-limited details, and the three-candidate cap is shared across all missing columns, filled round-robin so each missing column gets a turn.

Column errors carry a bounded dataset_context: up to ten column names and ten saved-metric names from the authorized dataset, names only — never SQL expressions. Suggested candidates are listed first so they are never cut by the bound (a hinted saved metric leads available_metrics the same way), and the error says Showing 10 of N columns or Showing 10 of N saved metrics when a list is partial. Context names are returned verbatim per the Tool Result Value Contract. "Did you mean" column candidates also preserve dataset spelling, including quotes and ampersands, with a 200-character bound per candidate. Use get_dataset_info for the complete schema.
