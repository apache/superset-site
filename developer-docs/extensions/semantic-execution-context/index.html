Semantic provider execution context

The unreleased SDK uses one SemanticLayer.from_configuration factory with required keyword-only cache_token: str and context: SemanticExecutionContext, and an optional credentials: SemanticCredentials | None = None reserved channel. Providers must migrate from the optional from_configuration_with_cache_token hook; there is no legacy-factory fallback. Configuration validation uses the provider's Pydantic configuration_class, without constructing a provider.

The frozen context contains the server-authenticated principal_id, sorted role_ids (including group roles), origin, is_guest, namespace, and an opaque identity_digest. It contains no tokens, passwords or Flask objects. For unchanged identity inputs, the digest is stable within an installation across processes and requests, is non-reversible, and rotates with the host SECRET_KEY. Use it only as an opaque partition token, not as a durable user identifier or an upstream credential. Providers must treat an unrecognized origin as unsupported; they must not substitute REQUEST or silently fall back to a supported origin. The digest excludes per-view RLS and origin. The host binds a layer and its views in one session memo, with distinct bindings for different contexts. Providers must retain the supplied context and metadata token with their bound instance.

The digest partitions installation, principal, roles and guest status, not individual guest tokens. Guests with the same roles and namespace share a digest even if their token's user, resources or row rules differ. It must not be used as a guest partition key. Semantic views refuse guest row rules; connection mode uses the same upstream account for every guest. Any future support for guest restrictions must include them in result-cache restriction material, not the provider catalog key. Non-connection methods remain disabled; enabling them must preserve the requirement to refuse guests.

ExecutionMethod.CONNECTION is the only enabled method. Providers declare supported_execution_methods (default: connection only). Under this method, results and catalogs must not vary with the context: discovery and execution use the configured connection credentials. The host passes credentials=None. Unsupported methods and explicit policy refusals fail before provider construction or reuse. This contract does not replace route and object authorization.

Include cache_token in metadata-cache keys before any lookup or eager discovery; never use secrets as cache keys. Views echo the captured token in metadata_cache_token. The context namespace uses SEMANTIC_LAYER_CACHE_NAMESPACE when set, otherwise an installation UUID read or created during app initialization when SEMANTIC_LAYERS is enabled, and held in app memory. Disabled startup skips namespace database access. If the runtime flag is enabled later, first semantic access loads or creates the same persisted identity across web and worker apps. If startup precedes database creation (for example, Helm's post-install upgrade), semantic access retries initialization once per access until it succeeds. Failed attempts remain fail-closed; no temporary identity is used. After successful initialization, namespace resolution needs no database access. An initialization retry uses an independent metadata-database connection in addition to any held by the caller. During repeated initialization failures or concurrent first access, a saturated pool can therefore time out; it never falls back to a temporary identity. Operators can configure a stable namespace to avoid the persisted fallback, or restart workers after the database upgrade completes. Callable tenant namespaces are evaluated at binding time and override the startup fallback. This is distinct from the existing metadata-generation namespace; chart, column-values and compatible-member cache keys are unchanged. Operator workspace namespaces must agree across processes.

The existing containment semantic_cache_scope, context-identity and provider-identity hooks remain in effect. Providers must supply complete, secret-free identity material or bypass containment. A dbt manifest or compiled catalog is still provider metadata and follows the same token partitioning rule. Both host contexts derive role IDs from effective roles, including group grants. The host's containment context identity (SemanticCacheExecutionContext.host_identity) includes an effective-role derivation marker, so context-scoped containment keys change even when the role list is empty. This prevents reuse of direct-only identities after group grants are revoked and causes a cold context-scoped containment cache; connection-scoped keys are unchanged. The SDK identity_digest is unchanged. The two SDK context types coexist and will be unified before any superset-core release. get_configuration_schema and get_runtime_schema remain class methods outside this instance-binding contract.

Only request/background origin inference is installed in this delivery; explicit MCP/export/async binders are deferred. Before enabling any non-connection method, the host must add async resolution pinning, effective-identity keys and refusal checks at every cache boundary, containment identity migration, namespace startup validation, and TTL enforcement. The reserved credentials channel and origin enum do not enable those methods by themselves.
